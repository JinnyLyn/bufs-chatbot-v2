# 서비스 동시 사용자 수용량 측정 (2026-09-01)

런칭 전 안정성 점검. "동시에 몇 명까지 서비스 가능한가"를 실측으로 답한다.
하네스: `eval_tools/_load_test.py` · 원본 데이터: `logs/load/*.json` (gitignore 대상)

## 품질 스펙 (SLO)

`eval_tools/kpi_profiles.yaml`의 `slo:` 블록이 기준 원본이다.

| 항목 | 기준 |
|---|---|
| 첫 응답 토큰 (TTFT) | p95 < 20초 |
| 전체 답변 완료 | p95 < 30초 |
| 오류율 (busy 거절 제외) | < 1% |

TTFT = 질문 전송부터 첫 `token` SSE 이벤트까지. 앞단 노드(요약·재작성·에이전트)는
프론트엔드 "생각 중" UI 뒤에 숨으므로, 사용자가 체감하는 "답이 나오기 시작한 시점"과 일치한다.

## 측정 방법

- closed-loop 가상 사용자 N명: 세션 발급 → qa100 골든셋에서 질문 → 답변 완료까지 대기
  → 5초 숙고 → 다음 질문. 실제 사용 패턴 근사.
- N = 1, 2, 3, 4, 6, 8 램프 (단계당 사용자별 6~8문항, 단계 사이 20초 쿨다운 —
  슬롯은 producer 스레드가 해제하므로 이전 단계 생성이 다음 단계로 새는 것을 방지).
- 측정 대상: 운영 중인 실서비스 그대로 (재시작 없음). 루프백 호출은 rate limit 면제.

### 환경 스냅샷

H100 NVL MIG 3g.47gb 슬라이스 · ollama 0.22.0 (:11500, `OLLAMA_NUM_PARALLEL` 미설정 =
기본 병렬 배칭) · qwen3.5:9b Q4_K_M · `LLM_NUM_CTX=16384` · `EMBEDDING_DEVICE=cuda` ·
백엔드 단일 uvicorn 프로세스 · `MAX_CONCURRENT_STREAMS=8` · main @ 8f80700 계열.

## 결과 — 동시 질문 램프

| 동시 사용자 | 요청 | TTFT p50 | TTFT p95 | 전체 p95 | 오류 | SLO |
|---|---|---|---|---|---|---|
| 1 | 6 | 6.0s | 6.6s | 8.7s | 0 | ✅ |
| 2 | 12 | 9.0s | 12.9s | 14.7s | 0 | ✅ 여유 |
| 3 | 24 | 14.4s | **19.9s** | 21.4s | 0 | ✅ 경계 |
| 4 | 24 | 18.7s | 26.7s | 29.1s | 0 | ❌ TTFT 초과 |
| 6 | 36 | 35.1s | 50.7s | 55.3s | 0 | ❌ |
| 8 | 48 | 50.4s | 76.5s | 77.9s | 0 | ❌ |

- **품질 수용량 = 동시 3명** (TTFT p95 19.9s로 20s 기준에 턱걸이 — 마진 없음).
- **여유 수용량 = 동시 2명** (p95 12.9s).
- 캡(8명)까지 오류 0건 — 성능은 우아하게 저하(순수 대기열 지연)하며 절대 깨지지 않는다.

### "동시 질문 N명" → "이용자 수" 환산

실제 이용자는 질문 사이에 읽고 생각한다. 이용자 1명이 평균 2분에 1질문, 답변 ~17초(3명
동시 기준 p50)라면 스트림 슬롯 1개가 약 7명을 감당한다:

> 지원 이용자 수 ≈ 동시질문수 × (질문간격 + 답변시간) ÷ 답변시간 ≈ 3 × (120+17)/17 ≈ **약 20명 상시 이용**

## 결과 — 과부하 (12명 동시 버스트)

16건 정상 응답 / 8건 정중한 busy 거절("지금 처리 중인 질문이 많습니다…", HTTP 503
`Retry-After: 10` 또는 SSE `error` 이벤트) / 실패·크래시 0건. 직후 `/health` 정상.
거절은 모델 작업 전에 발생하므로 비용이 거의 없다. 단, 캡이 찬 동안(8명 생성이 끝날
때까지, 최악 ~76초) 재시도도 계속 거절된다.

## 결과 — 소크 (동시 3명 × 30분)

271회 질문 / 271회 정상 응답 / 오류 0건. TTFT p50 13.3s · p95 17.0s · max 20.2s,
전체 p95 19.8s — 30분 내내 SLO 충족. 백엔드 RSS 3.37GB → 3.40GB(+0.7%, 누수 없음),
GPU VRAM 22.2GB → 24.2GB(+2GB, KV 캐시 정착 후 안정 — 지속 증가 아님).

정상 상태(steady-state)의 동시 3명은 p95 17.0s로 램프 측정(19.9s)보다 오히려 여유
있다 — 램프의 동기화된 도착이 최악 케이스였다는 뜻. 30분 내 지연 드리프트 없음.

## 캡(MAX_CONCURRENT_STREAMS=8)에 대한 주의

캡은 **남용 방지선**이다(스크립트 클라이언트가 GPU를 무한 점유하지 못하게 하는 상한).
**지연 제어 장치가 아니다** — SLO는 동시 4명에서 깨지고 캡은 9명째에서 작동한다.
품질 수용량이 3이라는 이유로 캡을 3으로 내리면, 오늘은 "조금 더 기다리면 되는" 동시
4명째 실사용자가 503을 받게 된다. 내리지 말 것.

## 재실행 방법

```bash
# 서비스가 떠 있는 호스트에서 (루프백 = rate limit 면제)
.venv/bin/python eval_tools/_load_test.py ramp --steps 1,2,3,4,6,8 --questions 6
.venv/bin/python eval_tools/_load_test.py overload --users 12 --questions 2
.venv/bin/python eval_tools/_load_test.py soak --users 3 --duration 30
```

주의: 부하 트래픽도 `logs/qa/`에 기록된다(백엔드 재시작 없이는 `CHAT_LOG_DISABLED` 적용
불가). 측정 직후 **session_id 기준으로만** 백업 후 정리할 것 — 결과 JSON의 `session_id`
필드가 하네스가 발급한 세션 목록이다. 질문 텍스트·시간대 필터는 금지: qa100 질문은
실제 학생 질문과 동일 문구라 실데이터를 지우고(오탐), 다른 합성 트래픽은 남긴다(미탐).
참고: 2026-09-01 파일은 ~13:16 이후 대부분 합성(측정+타 세션 픽스처, 픽스처는 PR #267로
차단됨)이며, 당일 실사용은 01:11–01:13, 09:25, 10:25, 11:07 등 산발 턴이 전부다.
