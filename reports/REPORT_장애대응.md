# 부산외대 학사 챗봇 — 장애 대응 계획

> 2026-09-04 · 운영 서버(maruvis.kr) 현황 점검 기준

## 한 줄 요약

장애를 세 갈래로 나눕니다. **우리 서버가 문제인 경우**, **우리 손 밖(Cloudflare·학교 네트워크)인 경우**, **답이 없는 질문인 경우**. 각 경우에 학생이 보는 화면과 우리가 하는 일을 정했습니다.

점검 결과 지금 가장 큰 구멍은 둘입니다. **백엔드가 죽어도 자동으로 다시 뜨지 않고 아무에게도 알림이 가지 않습니다.** 그리고 **밖에서 상태를 확인할 주소가 없어** 장애를 학생이 먼저 알게 됩니다. 이 둘을 1순위로 막습니다.

## 지금 구조와 장애가 나는 자리

학생 브라우저 → Cloudflare(maruvis.kr) → 터널(cloudflared) → 우리 서버(화면 :3000 / 백엔드 :8000 / AI 모델 ollama :11500, 공유 H100 GPU 한 조각)

| 어디가 죽나 | 학생이 보는 것 | 자동 복구 (현재) |
|---|---|---|
| 터널(cloudflared) | Cloudflare 영문 오류 페이지(502) | 있음 (5초 후 재시작) |
| 화면 서버(Next.js) | Cloudflare 영문 오류 페이지(502) | **없음** |
| 백엔드(FastAPI) | 페이지는 뜨지만 질문하면 "오류가 발생했습니다" 또는 무반응 | **없음** |
| AI 모델(ollama·GPU) | 질문 후 오류, 또는 '생각 중'이 끝나지 않음 | **없음** (공유 GPU라 남의 작업이 밀어낼 수 있음) |
| 서버 재부팅 | 전체 다운 → 자동 기동 (최대 약 5분) | 있음 (systemd 사용자 유닛, Linger 켜짐) |
| 동시 질문 8개 초과 | "지금 처리 중인 질문이 많습니다. 잠시 후 다시 시도해 주세요." | 해당 없음 (설계된 정상 동작) |

## 상황 1 — 우리 서버 문제 (응답 지연 · 응답 없음 · 프로세스 다운)

**감지와 자동 복구 (운영)**

- 2분마다 `scripts/healthcheck.sh`를 돌리는 systemd 사용자 타이머를 추가한다. 2회 연속 실패하면 `scripts/restart-all.sh`를 실행한다. 1시간에 3회 넘게 재시작하면 멈추고 사람을 부른다(재시작 폭주 방지).
- 실패·재시작·중단 때마다 팀 채널(Slack 또는 Discord 웹훅) 한 줄 알림. 웹훅 주소는 `scripts/env.local`에 둔다(커밋 금지).
- 백엔드에 `/api/health`를 추가한다. 응답은 `{"status":"ok"}`만(모델명·경로 등 내부 정보는 지금의 `/health`에 남기고 밖으로 내지 않음). 여기에 무료 외부 모니터(UptimeRobot, 5분 간격)를 붙여 문자·메일을 받는다. 터널·Cloudflare·학교망 장애까지 이 경로로 잡힌다.

**학생 화면 (프론트엔드 `useChat.ts`)**

- **45초 동안 진행 신호(status·token)가 없으면** 말풍선 아래에 "답변을 준비하는 데 시간이 조금 더 걸리고 있어요. 잠시만 기다려 주세요."를 띄우고 계속 기다린다. 30초에서 끊지 않는 이유: 몰리는 날에는 정상 답변도 78초까지 걸린다(부하 시험 p95, 동시 질문 8개). 30초에 끊으면 곧 도착할 답을 버리고 재시도로 부하만 더 얹는다.
- **120초를 넘거나 연결이 끊기면** 스트림을 닫고 "응답을 불러오지 못했어요. 잠시 후 다시 시도해 주세요."와 **[다시 시도]** 버튼을 보인다. 버튼은 마지막 질문을 그대로 재전송한다. 혼잡(503) 응답을 받은 경우에는 버튼을 10초 잠근다(서버가 보내는 Retry-After 값).
- 연결이 끊겼는데 부분 답변이 없는 경우(지금은 빈 화면)에도 같은 문구를 보인다.
- 오류 문구 아래에 사이드바와 같은 안내를 붙인다: "급한 문의는 학사지원팀 051-509-5182~5183 · 학사일정표 보기".

**백엔드**

- `TOOL_CALL_SOFT_TIMEOUT_S`(현재 꺼짐)를 켠다. 검색 반복이 이 시간을 넘기면 반복을 끊고 그때까지 모은 자료로 한 번에 답을 정리한다(`fallback_response`). 값은 40초부터 시작해 정답률 비교 후 확정한다(PR 정답률 칸 필수).

**수동 대응 (운영자, 5분)**

1. `bash scripts/healthcheck.sh` — 백엔드·AI 모델·화면 서버 중 어디가 죽었는지 확인.
2. `bash scripts/restart-all.sh` — AI 모델까지 죽었으면 `--with-ollama`.
3. `nvidia-smi` — 공유 GPU를 남의 작업이 채웠으면 우리 쪽에서 해결 불가. 서버 관리자에게 요청.
4. 30분 안에 복구가 안 되면 상황 2의 안내 페이지를 켜고, 학사지원팀에 "챗봇 점검 중" 공지를 요청한다.

**백업 서버**

두 번째 H100은 없습니다. 이전 운영 PC(RTX 4070 12GB, 작은 모델 프로파일)가 아직 있다면 대기 서버 후보입니다. 같은 터널 자격으로 그 PC에 cloudflared를 띄워 두고, 장애 때 H100 쪽 cloudflared를 멈추면 트래픽이 그쪽으로 넘어갑니다(전환 10분, 정확도·속도는 낮은 축소판). **PC가 남아 있는지, 전원·네트워크가 되는지 확인이 먼저입니다(미확인).** 없으면 백업 서버 대신 상황 2의 안내 페이지로 대신합니다.

## 상황 2 — 우리 손 밖 (Cloudflare · 터널 · 학교 네트워크 · 서버 전체 다운)

**지금 학생이 보는 것**: Cloudflare 기본 영문 오류 페이지(502·530). 우리 안내가 한 줄도 없습니다.

**조사 결과**: Cloudflare의 맞춤 오류 페이지(Custom Errors)는 무료 요금제에서 쓸 수 없습니다(Pro 이상). 대신 **Cloudflare Worker**로 같은 효과를 냅니다. 무료 한도는 하루 10만 요청, 요청당 CPU 10ms, 연결이 유지되는 동안 시간 제한 없음이라 스트리밍 답변도 그대로 통과합니다. 우리 트래픽(상시 20명 수준)은 하루 수천 건이라 한도에 여유가 있습니다.

**하는 일**

- `maruvis.kr/*` 앞에 Worker를 둔다. 평소에는 요청을 그대로 우리 서버로 넘기고, 서버 연결 실패나 5xx 응답이면 Worker 안에 내장한 HTML 안내 페이지 한 장을 대신 보낸다.
- 안내 페이지 내용: "챗봇 점검 중입니다. 잠시 후 다시 접속해 주세요. 급한 학사 문의는 학사지원팀(051-509-5182~5183) · 학사일정표 · 학교 홈페이지(www.bufs.ac.kr)".
- Worker에 **점검 모드 스위치**(환경변수 또는 KV 플래그)를 둔다. 계획 점검 때 켜면 서버가 살아 있어도 안내 페이지를 보인다.
- 배포 후 우리 서버를 실제로 멈춘 상태에서 안내 페이지가 뜨는지 확인한다.

**한계**: Worker는 우리 서버가 죽었을 때만 유효합니다. Cloudflare 자체 장애나 학교망에서 maruvis.kr 차단이면 우리가 할 수 있는 것은 없습니다. 이때는 학사지원팀의 공지 채널(학교 홈페이지 공지·학과 단체방)로 안내하는 것이 유일한 대응이므로, 담당 부서와 "챗봇 장애 시 공지 문구와 요청 경로"를 미리 합의해 둡니다.

## 상황 3 — 제공하지 않는 정보 질문 (식단 · 기숙사 · 장학 세부 등 자료 밖)

**원칙**: 우리 영역이 아님을 분명히 말하고, 우리가 답하는 범위를 알려주고, 갈 곳을 준다. 재검색은 늘리지 않는다(이미 검색어를 한 번 넓혀 다시 찾도록 되어 있고, 더 하면 지연만 는다).

**하는 일**

- 거부 답변 뒤에 **고정 안내 블록**을 붙인다. AI를 거치지 않는 후처리이므로 지어낼 위험이 없다. 거부 판정에는 이미 있는 `_REFUSAL_PATTERN`(`edges.py`)을 API 단에서 그대로 쓴다.
  > 이 질문은 챗봇이 다루는 학사 안내(수강신청·학사일정·성적·졸업요건·학적·등록) 범위 밖이에요. 아래에서 확인해 주세요.
  > · 학교 홈페이지 www.bufs.ac.kr · 학사지원팀 051-509-5182~5183 · 학부(과) 사무실 전화번호 보기
- 사이드바의 세션 목록 자리를 **주요 연락처 고정 표기**로 바꾼다: 학사지원팀, 학부(과) 사무실 전화번호(자료에 이미 있음), 학사일정표 링크(이미 있음).
- 질문 주제별로 담당 부서를 자동으로 골라 주는 것은 다음 단계로 미룬다. 주제 분류가 틀리면 엉뚱한 부서로 보내는 것이 더 나쁘다. 1차는 대표 번호와 전화번호 표로 충분하다.

## 학생 신고 채널 (조기 감지)

- 답변 말풍선에 👍/👎 버튼. 👎를 누르면 이유 하나 선택(틀림 · 느림 · 오류 · 기타)과 한 줄 메모. 사이드바에도 "오류 신고" 버튼을 두고 같은 곳으로 보낸다.
- 백엔드에 `POST /api/feedback`을 추가해 `logs/feedback.jsonl`에 쌓는다. 질문 원문이 함께 저장되므로 `logs/qa/`와 같은 취급(커밋 금지, gitignore 추가).
- 주 1회 집계 스크립트로 본다. **1시간에 👎가 5건 넘으면** 장애 신호로 보고 위의 알림 채널로 보낸다.
- 만족도 설문은 장애 대응과 별개라 이 계획에서 뺐다.
